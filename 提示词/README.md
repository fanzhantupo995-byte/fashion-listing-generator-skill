# 提示词适配层

这里放**各生成服务的提示词规则**。skill 主线（`SKILL.md`）不含任何服务名，服务差异全部收敛在这个目录。

## 为什么分两层

同一个「换一件衣服」的需求，不同模型的提示词语法、能吃的字数、参考图数量、尺寸档位都不一样。写进主线，主线就绑死了服务；不写，服务差异就漏在流程里。

所以定成：**主线管流程和铁律，适配层管服务特性。确定服务 → 载入适配文件 → 按它写提示词。**

## 文件命名

```
提示词/<服务>.md          服务适配：命令、上传、计费、平台限制
提示词/<模型>.md          模型适配：提示词语法、能力边界、文字规则、尺寸档位
提示词/seedream-5.0-pro.md
提示词/TokenGo.md
```

服务名 / 模型名，需要区分时加型号。文件名里的型号可以出现具体版本 —— 这是适配文件，绑定服务是它的本职。

**为什么再分一层**：一个服务可能接多个模型，同一个模型也可能被多个服务接。服务差异（怎么调、怎么传图、怎么计费）和模型差异（提示词怎么写、能吃几张图、尺寸档位）是两回事，分开写，改一个不影响另一个。

## 每个适配文件写什么

**服务适配（`<服务>.md`）**

- 上传与提交的命令、参数文件形态
- 计费方式、单张成本量级
- 平台限额与报错含义
- 结果下载与作品库

**模型适配（`<模型>.md`）**

- 该模型的提示词语法（图号指代方式、占位符格式、文字标注规则）
- 能力边界（组图支持与否、参考图上限、流式、联网）
- 提示词长度与字数限制
- 文字渲染规则
- 尺寸与分辨率档位
- 反面写法对照
- 结果下载与请求恢复规则；不添加生成结果自检或自动补正环节

## 实测优先于文档

**实测结论与官方文档冲突时，以实测为准，并把结论写进适配文件。**

模型的实际行为只有出图才知道。文档说「不支持某语法」但实测能用的，就按实测改，并在文件里注明「实测有效 + 证据」。反过来，文档写了但实测不行的，也要标注作废。

每条实测结论要能复现：用的服务、模型、参数、场景。

## 硬约束：不得出现具体商品

适配文件里**不能写具体商品名、颜色、款式、文案**。

- 示例一律用通用商品（如「纯棉圆领短袖」「米白色」「夏季百搭」），不写真实在做的商品
- 提示词结构里，商品信息是填空位，由实际项目的 `商品信息.md` 填进来
- 出现具体商品名 = 这个 skill 退化成单品专用，模块无法复用

判定标准：把商品名全部换成占位符后，规则是否还成立。成立才合格。

> 实测记录类内容可以写清「这套商品是单件还是套装」这类结构信息，但不得出现具体商品名与款式描述。

## 加一个新服务

1. 查该服务的官方提示词文档，把语法规则、能力边界、参数限制摘出来
2. 新建 `提示词/<服务>.md`（服务层）和/或 `提示词/<模型>.md`（模型层）
3. 官方文档链接附在文件末尾，便于日后复核
4. **`SKILL.md` 一个字都不用改**
